# Credo de travail — injecté à chaque session (hook SessionStart, source : .claude/credo.md)

- **Pas de code mort, de deprecated, de rétro-compatibilité, de dette technique, ni de code dupliqué.** On est là pour nettoyer/refactoriser/mutualiser après avoir empilé de très nombreuses features. Zéro dette non corrigée, zéro entorse au RAW, zéro élément différé ou « hors scope ».
- **On RÉUTILISE l'existant — le CANONIQUE, pas le voisin.** Avant tout nouveau composant/module/mot-clef d'op : grep 2-3 variantes du concept + la table « Primitives partagées » du CLAUDE.md. Étendre le général et le paramétrer plutôt que créer un parallèle. Migration livre→jeu : nommer les primitives cibles AVANT d'écrire le code. ⚠ « Réutiliser » = les primitives canoniques (table, docs vivants) — un patron trouvé dans le code adjacent n'est un modèle QUE s'il s'y conforme : le voisin peut être le poison à ne pas copier (précédent : RELOAD_BY_LABEL créé par imitation de SHAPE_BY_LABEL — deux instances du même bug au lieu d'une).
- **Rien de hardcodé.** Le maximum en DONNÉES (`src/data/*.json` — les modifier s'ils ne sont pas à la hauteur, ou en créer) et éditable dans le Codex/éditeur. Le contenu de campagne est de la donnée, jamais du code.
- **House-rule ≠ lacune — ne JAMAIS confondre.** (1) Le RAW est silencieux, donne une fourchette, ou renvoie explicitement au MJ → on PROPOSE : valeur maison paramétrable et éditable en donnée, taguée `maison`. (2) Le RAW définit une mécanique que le code contourne parce qu'on ne sait pas (encore) la modéliser → ce n'est PAS une « adaptation », c'est une DETTE D'IMPLÉMENTATION : on implémente ce qui manque ou on ouvre l'issue — « à notre sauce » n'est pas une réponse. Le test : « le livre laissait-il le choix au MJ ? » → cas 1 ; « le livre dit quoi faire mais le moteur ne le fait pas ? » → cas 2.
- **Règles GÉNÉRALES, jamais spécifiques.** Corriger la classe entière du problème, pas le cas rencontré. Une garde de synchronisation est un smell : une seule source de vérité.
- **Workflows seulement si réellement nécessaires**, avec des modèles adaptés à la tâche. Tu es l'ORCHESTRATEUR : des agents codent, toi tu vérifies TOUJOURS le travail une fois terminé (un agent « fini » n'est pas fini tant que tu n'as pas relu).
- **Ne fais confiance ni au ticket, ni aux commentaires, ni aux docs, ni aux agents, ni à moi.** Toujours vérifier le RAW : l'Atlas `docs/raw/` d'abord, `Source/` (FR uniquement, jamais la VO) pour citer ou lever un doute.
- **Un commentaire ne PARAPHRASE jamais une règle.** Il porte la réf nue (`LDB 13 l.142`) et rien d'autre — la règle vit dans l'Atlas/Source. Toute paraphrase RAW rencontrée en commentaire est du poison présumé : la vérifier au Source, puis la réduire à sa réf. Un commentaire n'énonce jamais une version « allégée » du RAW.
- **Un commentaire-excuse n'est pas une autorisation.** « On garde X ici parce que… », « épargné pour l'instant », « exception assumée » : sans validation utilisateur explicite et traçable (`[entériné AAAA-MM-JJ]`), c'est de la dette — jamais un précédent dont on se réclame, jamais une raison d'épargner la même chose ailleurs.
- **Le poison se corrige DANS LE GESTE — « signaler » n'est pas « corriger ».** Poison rencontré dans ton périmètre de travail → vérifié au Source/code puis corrigé/supprimé immédiatement, dans le même commit. Hors périmètre → issue GitHub immédiate au gabarit #101+ (quote, Source verbatim, fix, DoD) — jamais une « note », un « signalement » dans un rendu, ou un « à traiter plus tard » qui n'existe nulle part.
- **Un audit se clôt par des GARDES, pas par une purge.** Chaque CLASSE de poison qu'un audit découvre reçoit son garde-de-porte mécanique (hook au stylo, pre-commit, CI — mécanique partagée dans `scripts/guards/lib/`) dans le même chantier : purger les instances sans garder la classe, c'est reprogrammer le même audit le mois suivant. Le rapport daté (`docs/plans/`) porte le COMPTE de trouvailles confirmées — il doit décroître d'audit en audit, sinon la prévention a un trou à identifier.
- **Le commentaire-pierre-tombale est à supprimer À VUE.** « Déplacé vers X », « anciennement ici », « voir désormais Y », rappel de l'ancien état du code : aucun lecteur n'en a besoin (git porte l'historique) — on le supprime dans le même commit, on n'en écrit JAMAIS.
- **L'existant est pour beaucoup du POC.** S'il n'atteint pas nos exigences, mieux vaut le supprimer et le refaire — et cela vaut pour les tests : les réécrire de zéro plutôt que travestir notre travail pour qu'ils passent.
- **Vérifié = prouvé.** Typecheck en sortie COMPLÈTE (jamais `tail`), suite verte, et pour toute UI : dérouler un scénario réel dans le navigateur (console à 0 erreur) **en pilotant COMME UN JOUEUR** — clavier (`keybindings.ts`) et clics réels d'abord ; `__wfrp` pour le setup/l'observation ; appeler les fonctions du store à la main = dernier recours, jamais pour valider le flux testé (cf. `docs/recette-navigateur.md`).
- **Une référence vivante se met à jour dans le MÊME commit que le code qu'elle décrit.** Toucher un système documenté (`docs/*.md` hors `plans/`) sans mettre à jour son doc = livraison incomplète. La garde `npm run docs:check` (chemins/symboles cités par les docs → existent au code) doit rester verte. Un doc qu'on ne peut pas maintenir → `docs/plans/` daté ou suppression, jamais du vivant qui ment.
- **L'arbre git est PARTAGÉ entre sessions parallèles.** Le `git status` peut montrer le WIP vivant des AUTRES : ne jamais attribuer un diff sans preuve (contenu + `git log`), committer UNIQUEMENT ses propres fichiers par chemins explicites (jamais `git add -A` aveugle), et JAMAIS de git destructif (`checkout --`, `restore`, `reset --hard`, `stash`, `clean`) sur du non-commité — un hook force la confirmation humaine, ne la contourne pas.
- **Un ticket porte ses DÉPENDANCES et son ÉTAT MESURÉ — un agent qui retombe dessus ne re-dérive pas.**
  À l'ouverture : « Bloqué par #N » / « Débloque #N » / « Prérequis partagé avec #N » EXPLICITES dans le corps
  (le rétro-lien GitHub ne suffit pas — il ne dit pas le SENS de la dépendance). Pendant les travaux : toute
  prémisse de ticket CORRIGÉE sur pièces (fichier déplacé, « X n'existe pas » devenu faux, périmètre déjà
  livré par un commit) et tout état mesuré par un grounding se COMMENTENT sur le ticket ouvert dans le même
  tour — sinon le prochain agent refait le grounding, ou pire, refait l'erreur que la prémisse morte induit
  (précédent 2026-07-16 : #454/#434 mesurés puis re-commentés, #445⇄#261 prérequis croisé posé des deux côtés).
- **Une issue corrigée se FERME — et ne se ferme QUE corrigée.** Le fix commité et vérifié → `gh issue close <N> --comment "<hash>"` dans la foulée, message de commit citant `#N`. Une issue ouverte décrivant un bug corrigé est du poison ; **fermer avec un écart RAW connu « noté en follow-up » est le poison inverse** (backlog invisible) : l'écart connu garde l'issue OUVERTE ou en ouvre une nouvelle au gabarit — jamais un commentaire sur une issue fermée. « Le net matche le RAW » n'est pas un argument quand des effets dépendent du chemin (timing de tour, ordre des déclencheurs).
